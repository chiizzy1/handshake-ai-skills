# Project Mark — Task Builder

Mark is task authoring: real evidence, a realistic decision request, reproducible
reference answers and an observed model evaluation. It is not a rating task.

Read [operative rules](../shared-references/canonical-rules.md) first. The
September 5 update permits **1–3 deliverables** for new tasks, removes assigned
families and per-file ask quotas, retains **25+ criteria**, and requires the
initial **Responses 1 and 2 to average below 70%**. Older tasks retain their
applicable old specification. Do not overwrite their contracts to match a new
one.

## Start with the evidence and analytical objective

For an existing slot, read its objective and task version before committing a
build. Source screening can proceed without claiming a slot; mark it as
exploratory and do not change a live assignment to fit an already-built package.

Use [data selection](references/data-selection.md) to inspect candidate
sources and [the runbook](references/new-task-runbook.md) for the practical
sequence. Research may suggest failure mechanisms; only matched current
rollouts demonstrate them.

The tasks 01 and 02 records show those specific designs were solved. They do
not prove that a domain, file format, or reasoning family can never work.
Read the current interpretation at the top of
[rollout lessons](../shared-references/rollout-lessons.md); older entries are
historical and sometimes overgeneralized.

## Work through the routed skills

- **mark-input-package:** verify actual public tables, necessary variables,
  joins, design documentation, license and source terms. Preserve raw evidence.
- **mark-trap-designer:** compute defensible and plausible shortcut analyses;
  establish a consequential difference and inspect uncertainty/alternatives.
- **mark-prompt-writer:** write a natural business request with enough scope to
  determine the answer, without narrating the solution.
- **mark-golden-builder:** independently establish correctness, then produce
  exactly the requested final files from consistent computed results.
- **mark-validator:** record reproduction, robustness, blind screening and the
  official platform gate separately.

## Invest in the right order

Build a small internal analytical prototype before a full submission package.
Use fresh blind solvers with normal tools and no answer key. If both solve the
analysis cleanly, retire or materially redesign that concept before polishing.
This is a local screening recommendation, not a platform rule.

Prefer difficulty in connected empirical structure: assignment and follow-up,
cohort composition and outcome timing, information availability and validation,
or another decision-relevant interaction. A lookup moved into SQLite, added
duplicates or more files has no demonstrated difficulty benefit by itself.

Before submission, satisfy inherited input requirements or current UI
replacements, run official evaluations and produce polished business-realistic
goldens. LLM assistance is permitted; fabrication of empirical evidence is not.

## Reporting and authorization

Carry out file changes and reversible local work when the user authorizes them.
Never claim a download, test, screen, rollout or approval that did not occur.
Report the selected source/concept, evidence for its choice, artifact paths,
checks actually run and outstanding dependencies. Follow current UI workflow
rather than reconstructing missing platform steps from old examples.
